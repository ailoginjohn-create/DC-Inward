# Changing the Database Provider

The application is database-agnostic. Data access goes through repository interfaces,
and EF Core migrations are generated per provider. Only `Database:Provider` and a
connection string change at runtime.

## Supported providers

| Provider | EF Core package | `Database:Provider` value |
| --- | --- | --- |
| SQLite (default) | Microsoft.EntityFrameworkCore.Sqlite | `Sqlite` |
| PostgreSQL | Npgsql.EntityFrameworkCore.PostgreSQL | `Npgsql` |
| SQL Server | Microsoft.EntityFrameworkCore.SqlServer | `SqlServer` |
| MySQL | Pomelo.EntityFrameworkCore.MySql | `MySql` |

All provider packages are already referenced by `InwardDC.Infrastructure.csproj`.

## Steps

### 1. Configure the connection string

Edit `src/InwardDC.App/appsettings.json`:

```json
{
  "Database": {
    "Provider": "Npgsql",
    "ConnectionString": "Host=localhost;Port=5432;Database=inwarddc;Username=inwarddc;Password=***"
  }
}
```

`IDatabaseProvider` implementations translate the generic connection string into the
provider-specific form. The `App:DataDirectory`/`INWARDDC_DATA_DIR` settings continue to
control where attachments, backups and logs are stored.

### 2. Generate the migration

From the repository root (installed `dotnet-ef` 8.0.x as a global tool):

```bash
export DOTNET_CLI_TELEMETRY_OPTOUT=1 DOTNET_NOLOGO=1 TERM=xterm LC_ALL=C
export PATH="$PATH:/root/.dotnet/tools"

dotnet ef migrations add InitialCreate \
  --project src/InwardDC.Infrastructure \
  --startup-project src/InwardDC.Infrastructure \
  --context AppDbContext
```

Migrations are written under `Migrations/` per provider (the infrastructure project is
used as both the migrations and design-time startup project via
`InwardDcDesignTimeFactory`, which reads `Database:Provider` from its own
`appsettings.json`).

### 3. Apply

`MigrationRunner` applies pending migrations automatically at app startup, so simply
launching the application creates/upgrades the target database. You can also apply
manually:

```bash
dotnet ef database update \
  --project src/InwardDC.Infrastructure \
  --startup-project src/InwardDC.Infrastructure \
  --context AppDbContext
```

### 4. Migrating existing SQLite data

1. Take a backup (Backup & Restore screen) to get a `.zip` containing
   `InwardDC.db` + `settings.json`.
2. Point the app at the new provider, launch once so the schema is created, then
   restore the backup — the restore flow reloads settings and re-seeds configuration.

For large data sets, script an ETL between databases instead; the schema above is a
starting point for mapping.

## Caveats

- **MySQL filtered indexes**: MySQL does not support filtered unique indexes, so the
  soft-delete unique constraints are plain. Re-using a deleted code/number requires
  manual recycling (or a `Removed_*` suffix strategy).
- **Decimal precision**: `ConfigureConventions` pins `decimal` columns to
  `decimal(18,4)` on providers that need it.
- **GUID generation**: SQLite uses `TEXT`; keys are generated by the application, so no
  provider-specific default is required.
